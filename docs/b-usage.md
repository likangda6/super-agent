# Super-agent 使用手册

本手册说明如何通过 GitHub 使用本仓库的 Super-agent 机器人（@testAgent-hub）：从发起任务到验收结果共五节，每节附一个可直接参考的示例。机器人只处理允许名单内用户提出的请求。本仓库仅用于原型验证，请勿用于生产用途。

## 发起

在仓库的 Issues 页点击 New issue，标题用一句话写明要完成的事情，例如「新建 docs/b-usage.md」。正文 @testAgent-hub 并描述需求，一次只做一件事。请在 Issue 中说明这是新建、修改还是删除，避免机器人猜测意图；建议分点列出目标文件、章节标题、内容要点和验收标准。只有一句话的需求也能处理，但机器人需要更多猜测，返工概率更高。提交后机器人会回复确认，在 `agent/` 开头的分支上完成修改，并以 Pull Request 交付。如果任务较大，拆成多个 Issue 分别提交，比一个 Issue 塞进多件事更容易验收。需求越具体，结果越容易核对；不要在 Issue 中粘贴令牌或其他敏感信息。

示例：

```markdown
@testAgent-hub 新建 docs/b-usage.md，写 5 节使用手册（发起、查看、追问、取消、验收），每节 200 字并配一个示例
```

## 查看

进度会留在原 Issue：机器人先回复确认，完成或需要人决定时再给出 PR 链接和说明，不必反复催促或另开 Issue。Issue 的评论和时间线就是处理记录；PR 标题通常与任务对应，找不到时可在 PR 列表按作者筛选。打开 PR 后，可在 Conversation 看讨论、在 Files changed 看改动、在 Checks 看自动化检查；检查未通过时，PR 页面会标出失败项，可在评论中请机器人修复。Commits 记录每次修改，方便对照。有面板权限的同事可打开 Superagent，在 Overview 看需要处理的条目，在 Execution 看工单状态。长时间没有回复时，确认正文是否提到 @testAgent-hub、自己是否在允许名单内。

示例：

```bash
ISSUE=42  # 换成实际 Issue 编号
gh issue view "$ISSUE" --repo likangda6/super-agent --comments
gh pr list --repo likangda6/super-agent --author testAgent-hub --state open
```

## 追问

任务进行中需要补充或修改要求时，直接在原 Issue 或 PR 下评论并 @testAgent-hub，说明要调整的内容即可，不要另开 Issue。机器人会接着处理这条消息：范围内的改动直接做，超出范围或属于其他任务的，会说明原因并另行安排。也可以追问进度或请它解释某处改动；处理后会回复说明改了什么，若认为不必改也会给出理由。补充要求尽量具体到文件和段落，或引用具体行号，避免只写“再改改”，以减少来回确认。范围内的修改会更新到同一个 PR，不会另起任务。如果原任务已合并而你又有了新需求，仍建议新开 Issue 独立跟踪。

示例：

```markdown
@testAgent-hub 第二节「查看」请补一句：在 PR 的 Checks 里查看检查结果；其余章节保持不变。
```

## 取消

需要停止任务时，在原 Issue 中明确写出取消指令并 @testAgent-hub，例如“取消这个任务，不用继续了”。机器人会停止后续工作，已经完成的部分和当前 PR 都会保留。不要只关闭 Issue 或保持沉默，否则运行中的任务可能继续。也可以在 Superagent 面板的 Execution 页打开对应工单并点击停止（Stop）。取消只影响这个工单，不会删除已有代码或 PR；需要时你可以再手动关闭 PR。被取消的工单不再接收后续消息；若仍要继续，需要重新提出请求，建议另开一个 Issue 以免与旧任务混淆。团队协作时，可在 Issue 中简要说明取消原因，方便其他人了解上下文。

示例：

```markdown
@testAgent-hub 取消这个任务，不用继续了；已提交的草稿 PR 保留即可。
```

## 验收

机器人报告完成后，先读 Issue 里的完成说明，再打开 PR 逐项核对：改动文件是否符合预期，每节内容和示例是否齐全，Checks 是否通过，以及是否夹带无关修改或敏感信息。若 PR 仍是 Draft，说明任务尚未完成，不要合并。如果发现没有按需求完成，不要直接合并，先说明差距让它补充；需要调整的地方用“追问”的方式评论。确认无误后由人合并 PR，机器人不会自行合并；合并前可请另一位同事复核。合并后 PR 会标记为 Merged，可作为任务的最终记录，随后关闭 Issue。建议在发起时就写清验收标准，避免只凭印象判断。

示例：

```markdown
- [x] 新增 docs/b-usage.md，包含发起、查看、追问、取消、验收五节
- [x] 每节约 200 字，并各配一个示例
- [x] 只改动 docs/b-usage.md，没有无关修改或敏感信息
```
